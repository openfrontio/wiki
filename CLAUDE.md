# CLAUDE.md — OpenFront Wiki

Project-specific rules for working in this repo. These are hard constraints —
follow them exactly.

## What this is

A **static** rebuild of the OpenFront wiki: Astro 5 + Tailwind v4, output to
`dist/`, auto-deployed to **Cloudflare Pages** (Git integration) on every push to
`main`. Homepage is `src/pages/index.astro`; articles are generated by
`src/pages/[slug].astro` from two sources (see "Content" below).

## Hard constraints

### 1. Stay a static site — always

- The build MUST remain a pure static export (`astro build` → `dist/` of HTML/CSS/JS/assets).
- **Do NOT** add an SSR adapter, set `output: "server"`/`"hybrid"`, add server
  endpoints/API routes (`src/pages/**/*.{js,ts}` that return responses), use
  `export const prerender = false`, or introduce any runtime backend, database,
  or server process.
- No build step may require network access to a private service. Anything dynamic
  must be done client-side with public data, or precomputed at build time.
- Cloudflare Pages serves static files only — if it can't be served as a flat file
  from `dist/`, it doesn't belong here.

### 2. No secrets — ever

- Never commit API tokens, keys, passwords, or `.env` files with secrets.
- The site needs **no** secrets to build or run. Deployment auth lives in
  Cloudflare's dashboard, not in this repo.
- Don't add code that reads secret env vars at build or runtime.

### 3. Verify every rendered change before committing

Before committing any change that affects the rendered site (pages, components,
styles, content):

```bash
npm run build                       # must succeed with no errors
npx astro preview --host --port 4321
```

Then look at the affected pages. Preferred: the headless-browser skill in
`.claude/skills/run-openfront/` (`shot.mjs <url> <out.png> 1440 1000`, and
`390 844` for layout changes) — read the screenshot and check the console
output it prints is clean. If Playwright cannot launch on the machine (seen on
Windows: `spawn UNKNOWN`), use the in-app browser instead: navigate to the page,
take a screenshot, and check `read_console_messages` for errors. A change is not
"done" until it has been seen rendered.

Also sanity-check internal links: every `](/Slug)` in a changed page should have a
matching `dist/Slug/index.html`.

## Content

Two sources feed the article route:

**1. Game wiki pages — `src/content/wiki/*.md` (hand-edited Markdown).**
This is the source of truth for every game/maps/guides/updates page. Each file is
an Astro content-collection entry with frontmatter:

```yaml
---
title: "Page Title"
section: "Maps"          # sidebar group: Maps, Buildings, Units, Combat & mechanics,
                         # Game modes, Guides, Updates, Meta & community
cats: []                 # optional topical categories shown as pills
stub: true               # optional
---
```

The file name is the URL slug (`Yangtze_River.md` → `/Yangtze_River`); keep the
MediaWiki-style underscores. Headings carry explicit ids (`## Nations {#Nations}`)
so anchors stay stable. Raw HTML (figures, wikitables, hatnotes) is allowed and is
how images and tables are done. Edit these files directly — there is no crawl step
any more. When you add a page, also add its slug to `scripts/game-categories.json`.

The upstream MediaWiki at `openfront.miraheze.org` is dormant; the old
crawl/`prepare-content.mjs` pipeline and `scripts/legacy-pages.json` are kept only
for history and must not be re-run over the Markdown collection.

**2. OpenFront Masters (esports) — `src/data/pages.json` (generated).**
A Liquipedia mirror: `scripts/liquipedia-fetch.mjs` (API-only, rate-limited,
cached — never scrape HTML; keep the custom User-Agent) → `scripts/prepare-liquipedia.mjs`
→ `pages.json`. It is a manual-refresh snapshot; re-run the scripts to refresh.
Images use a filename allow-list (`isHostableImage`). Don't hand-edit `pages.json`.

### Refreshing the wiki for a new game version

New versions are authored by hand from the official release notes at
`https://openfront.io/#modal=news` (GitHub releases have the same text). Follow the
existing pattern (see the v33/v34 commits):

1. `src/content/wiki/Update_NN.0.md` — full changelog page, same section layout as
   the previous one.
2. One page per new map, cloned from an existing map page. Data comes from the game
   repo: `map-generator/assets/maps/<id>/info.json` (name, nations,
   `multiplayer_frequency`, categories) and `image.png` → `public/images/<Name>_map.webp`
   (use `sharp`, resize to 1280px wide, quality ~82; the `<img>` keeps `width="640"`).
3. `Maps.md` — add a "New in Update NN.0" section; `Update_History.md` — new table
   cell + section; `Map_Updates.md`.
4. Mechanics pages the notes touch. For anything numeric, read the actual game
   source rather than paraphrasing the notes: `src/core/configuration/Config.ts`
   (costs, attack logic, troop/gold rates, trade-ship saturation) and
   `src/core/execution/**` (nation AI etc.).
5. `src/pages/index.astro` — `updates[]` fallback entry and the `majorUpdate` copy.
   The homepage also fetches live GitHub releases client-side and links each
   `0.NN.x` release to `/Update_NN.0` when that page exists.

